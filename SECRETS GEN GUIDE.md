# Secrets generation guide

Every random value baked into `.env.example` is a local-development secret: all host ports bind to
127.0.0.1 and nothing is reachable from outside the machine. They are committed so a first run works
without a generation step. To regenerate any of them, use the one-liner below, put the value in `.env`,
and (for anything a service stores at first start) recreate that service's data volume.

| Variable(s) | Format | Command |
|---|---|---|
| `POSTGRES_PASSWORD`, `CUSTODIAN_DB_PASSWORD`, `LEDGER_DB_PASSWORD`, `AUDIT_DB_PASSWORD`, `KEYCLOAK_DB_PASSWORD`, `INFISICAL_DB_PASSWORD`, `LITELLM_DB_PASSWORD`, `MLFLOW_DB_PASSWORD`, `LANGFUSE_DB_PASSWORD`, `OPENMETADATA_DB_PASSWORD` | 48 hex chars | `openssl rand -hex 24` |
| `MINIO_ROOT_PASSWORD`, `AUDIT_MINIO_PASSWORD`, `LANGFUSE_MINIO_PASSWORD`, `REDIS_PASSWORD`, `KEYCLOAK_ADMIN_PASSWORD`, `INFISICAL_ADMIN_PASSWORD` | 48 hex chars | `openssl rand -hex 24` |
| `INFISICAL_ENCRYPTION_KEY` | 32 hex chars (16 bytes), required by Infisical | `openssl rand -hex 16` |
| `INFISICAL_AUTH_SECRET` | base64 of 32 bytes | `openssl rand -base64 32` |
| `LANGFUSE_ENCRYPTION_KEY` | 64 hex chars (32 bytes), required by Langfuse | `openssl rand -hex 32` |
| `LANGFUSE_SALT`, `LANGFUSE_NEXTAUTH_SECRET`, `CLICKHOUSE_PASSWORD` | 32 hex chars | `openssl rand -hex 16` |
| `LANGFUSE_SECRET_KEY` | `sk-lf-` + 32 hex | `echo "sk-lf-$(openssl rand -hex 16)"` |
| `LANGFUSE_PUBLIC_KEY` | `pk-lf-` + any id | `echo "pk-lf-$(openssl rand -hex 8)"` |
| `LITELLM_MASTER_KEY`, `LITELLM_SALT_KEY` | must start with `sk-` | `echo "sk-master-$(openssl rand -hex 16)"`, `echo "sk-salt-$(openssl rand -hex 16)"` |
| `KC_CLERK_PASSWORD`, `KC_CONTROLLER_PASSWORD`, `KC_CFO_PASSWORD`, `GRAFANA_ADMIN_PASSWORD`, `LANGFUSE_ADMIN_PASSWORD` | human-typable demo passwords | `python3 -c "import secrets; print(secrets.token_urlsafe(12))"` |

Values that are generated at runtime and never baked in:

| Value | Generated by | Where it lives |
|---|---|---|
| `SPIRE_JOIN_TOKEN` | `spire-server token generate` in `infra/scripts/setup-spire.sh` | `.env` (single use, 10-minute TTL) |
| `INFISICAL_ADMIN_CLIENT_ID/SECRET` | Infisical, via `infra/scripts/bootstrap-infisical.sh` | `.env` |
| `*_CLIENT_ID/SECRET`, `INFISICAL_PROJECT_*` | Infisical, via `infra/scripts/provision-infisical-identities.py` | `.env` |
| `LEDGER_API_KEY`, `VENDOR_LOOKUP_API_KEY` | `secrets.token_hex(32)` in `provision-infisical-identities.py` | Infisical only (never in `.env`) |
| `LITELLM_KEY_*` | LiteLLM `/key/generate`, via `infra/scripts/provision-litellm-keys.py` | `.env` |

Changing a password after first start: Postgres roles, MinIO users, Keycloak users and Infisical keep
the value they were created with. Either change it inside the service too, or remove the relevant volume
(`docker volume ls | grep custodian_`) and redo the first-run sequence. Note that the `minio-data`
volume holds audit objects under COMPLIANCE retention; deleting the volume removes them at the
filesystem level, which is outside what S3 object lock can prevent.
